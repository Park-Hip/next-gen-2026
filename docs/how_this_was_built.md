# How this was built

Who did what, which AI tools were used, and how their output was checked.
The competition allows any AI tool but requires declaring the tools that shaped the result and how their output was verified ([`ai_policies.md`](competition/ai_policies.md)).
Mission 2 does not submit the evidence log, so this page is its public summary.

## Responsibility

I made every decision and technical choice in this system.
AI tools drafted, researched and wrote code under my direction.
I reviewed the content of every issue, every implementation plan and every pull request before it went ahead.

## Tools and models

Two separate uses of AI: the tools that built the project, and the models inside the product.

### AI used to build the project

| Tool | Model | Used for |
|---|---|---|
| Pi, a terminal coding agent, calling Claude through the claude-bridge extension | Claude Opus 5.5 | Plans, implementation plan comments, research orchestration and source checking, ADR drafts from Hiep's answers, code, reviews, these documents |
| Claude Code (CLI), and Pi as above | Claude Sonnet 5.5 | Building some issues from their approved plans |
| Pi, through the ModelScope provider | DeepSeek V4 Pro | Building some issues from their approved plans |
| Pi, as `researcher` subagents | Agnes 2.5 Flash, at max reasoning | Web search lanes for the four technical research questions; Claude then opened every source itself |
| Lavish | None | Hiep's review notes, written directly on the draft plan |
| GitHub Actions | None | Runs the test suite on every PR |

Every unit, person, document and number in the data is simulated ("giả lập"); no real Appota data and no personal data was given to any AI tool.

### LLMs inside the product

| Step | Model | Its job |
|---|---|---|
| 5, search | `gemini-embedding-001` | Embeds the chunks and the question; ranks only chunks inside the asker's scope (ADR 0002) |
| 6, answer | `gemini-3.5-flash-lite`, medium thinking | Writes the answer from the retrieved chunks, citing chunk ids and quoting each clause (ADRs 0003, 0008) |

Neither model decides access, validity, applicability, precedence or the card; see [`architecture.md`](architecture.md).

## Workflow

The rules for every AI agent working on the repository are in [`AGENTS.md`](../AGENTS.md).

1. **Issue.** Every code change starts from a GitHub issue made with a form in `.github/ISSUE_TEMPLATE/`.
2. **Plan comment.** Before coding, the agent posts an implementation plan on the issue: what it checked, the decisions Hiep must take with a recommendation for each, the files, the tests and how to verify.
   Example: [the plan for the evaluation harness](https://github.com/Park-Hip/next-gen-2026/issues/14#issuecomment-6159868792).
3. **Hiep's decision.** Hiep answers each decision, and the comment is edited to record his answer in his words; the work follows the comment.
   A choice with real alternatives first goes through a research issue: the write-up in [`docs/research/`](research/) gathers options and sources, and the ADR in [`docs/decisions/`](decisions/) records Hiep's decision and his reasons, never reasons the AI wrote for him.
4. **AI builds.** The agent builds the issue on its own branch and opens a PR that says `Closes #<issue>`.
5. **CI and "Hiệp's check".** GitHub Actions runs the tests; the PR template ends with three boxes Hiep ticks before he merges: he read every changed file and can explain it without AI, he ran the verification himself, and the decisions match what he decided.
   Only Hiep merges.

## How results were checked

- **Tests.** The deterministic test suite runs the rules on every test row, checks that nothing outside the asker's scope is ever retrieved or cited, and checks step 7 against invented citations and wrong quotes; it uses a fake embedder and a fake LLM, so it needs no key.
  A parity test runs the same rows through the script the Mission 1 design was checked with.
- **Breaking the code on purpose.** For the rules and the leak guard, the agent removed one check at a time and confirmed that a test failed, then restored it; each case is recorded in the evidence log.
- **The real model.** The evaluation harness asks every test row through the same code path as the page and writes a [test report](mission2/test_report.md) in the brief's format; Hiep reads every answer by hand for faithfulness.
- **Research.** Search subagents only proposed sources; Claude opened each source and copied the quote from the opened page, and claims that did not hold up are listed in each write-up rather than used.
- **Facts in documents.** Numbers on these pages come from a run or a file, and the traces in `architecture.md` are generated by `scripts/show_scope.py --why` and copied from the committed run.

## The evidence log

Every AI session that changed the project has one line in the evidence log: date and time, tool and model, the task, Hiep's decision and how the result was checked.
`scripts/ai_sessions.py` lists the recorded sessions of Pi and Claude Code, so the log can be checked against them.
The Mission 2 log is a local file that Hiep chose not to publish (13/10/2026); he can show it in the PITCH round.
The Mission 1 evidence log, as submitted, is in [`docs/mission1/submitted/`](mission1/submitted/).
